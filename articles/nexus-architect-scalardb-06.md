## 前後比較で見るリファクタリングの効果測定

:::message
分析・設計・実装を経て、POSシステムの構造がどのリスクをどの程度下げたのかを前後比較と評価指標で確認します。

実装編では、Nexus Architectの設計書を入力として、Compound Engineeringを使いながら`pos-microservices`を実装していった流れを見ました。

このページで見ていく改善効果について、設計・評価ツールである「Nexus Architect」によって算出された指標の数値を先にまとめると、以下のようになります。


| 指標 | 評価 |
|---|---:|
| DDD準拠度 | 86.8% |
| MMI平均 | 77.4% |
| 総合評価 | 82.1% |
| アーキテクチャ層 | 5/5 |
| shared/common | 96% |
| 境界コンテキスト間のドメインモデル共有 | ゼロ |

特に大きい改善は、以下の3つです。

- `OrderService`、`CheckoutSaga`、`ReturnSaga`に集中していた責務が13サービスへ分散された
- ScalarDB、Outbox、Saga、CQRS Read Modelによって、一貫性と副作用の扱いが明確になった
- 4層レイヤリング、ポート/アダプター、境界コンテキスト分離によって、悪い実装が入りにくい構造になった

![pos-before-after](/images/legacy-refactoring-nexus-scalardb/pos-before-after.png)
*before / after 比較図*

ここまでの流れを振り返ると、今回のリファクタリングは単にコードを分割しただけではありません。

まず、現状分析では`OrderService`、`CheckoutSaga`、`ReturnSaga`に責務が集中していることが明らかになりました。次に、設計フェーズでは境界コンテキスト、ScalarDBによるトランザクション境界、Outbox、Saga、CQRS Read Model、HA/DR、可観測性まで含めたターゲットアーキテクチャを作りました。そして実装フェーズでは、その設計を13サービス、共通ライブラリ、ScalarDBスキーマ、Docker Compose、CI/CD、Kubernetes、フロントエンドまで落としています。

このページでは、その結果として何が改善されたのかを見ていきます。

重要なのは、評価が感想ではなく、構造に基づいている点です。

たとえば、ドメイン層にScalarDBの型が漏れていないか、他サービスのドメインモデルを直接importしていないか、循環依存がないか、OutboxがDual-Writeを防げているか、といった観点で改善効果を確認できます。

つまりこのページでは、リファクタリングの効果を、きれいになった気がするではなく、どの構造が、どのリスクを、どの程度下げたのかという形で読み解いていきます。


### 改善効果の全体像

DDD準拠度86.8%は、Strong DDD alignmentと評価されています。

MMIはModularity Maturity Index（モジュール成熟度指標）の略であり、モジュールとしての成熟度や独立性（マイクロサービスへの移行しやすさ）を見る指標として使われています。平均77.4%という数値は、全サービスが完全に同じ成熟度という意味ではありません。むしろ、`checkout-orchestrator`や`return-service`のようにSagaの性質上どうしても複数サービスに依存するモジュールがありながら、全体として高い独立性と凝集度を保てている、という読み方が自然です。

総合評価82.1%は、移行準備ができている状態として扱われています。

この時点で注目したいのは、スコアの高さそのものよりも、どの部分が強みとして確認できるかです。

特に以下の点が大きく改善されています。

- 4層レイヤリングが全13サービスに一貫適用されている
- ポート/アダプターパターンで技術詳細が閉じ込められている
- 依存方向がドメイン層へ向かっている
- 集約設計とScalarDBトランザクション境界が対応している
- 13境界コンテキストがコード、データ、通信の各層で分離されている
- 28個のドメインイベントがOutboxで原子的に発行される
- shared/common、shared/outbox、shared/saga、shared/securityが再利用基盤として機能している
- OpenTelemetry、SLI/SLO、Argo Rolloutsなどの運用基盤も整っている


#### 最大の改善は構造的に悪い実装をしにくくしたこと

今回の改善で最も重要なのは、良い設計を個人の自制で維持しているのではなく、アーキテクチャが悪い実装をできないように構造的に強制している、という点です。

レガシーシステムでは、設計上はきれいにしたくても、構造がそれを支えていませんでした。

ServiceからDAOを直接呼べる。SagaからMySQLとPostgreSQLの両方を触れる。Dashboard集計を`OrderService`に足せる。監査ログや通知イベントを業務更新とは別経路で書ける。こうした構造では、担当者が注意していても、時間が経つほど責務が混ざります。

今回のリファクタリング後は、同じ問題が起きにくい形に変わっています。

| 以前起きやすかったこと | 改善後に防ぐ仕組み |
|---|---|
| ドメイン層がDB実装を知る | ポート/アダプターパターン |
| Controllerにビジネスロジックが入る | domain/application/infrastructure/presentationの4層 |
| 他サービスのドメインモデルを直接使う | shared/*のみを共有し、各BCのモデルは非共有 |
| 外部APIをDBトランザクション内で呼ぶ | Outbox ACL Worker |
| データ更新とイベント発行がずれる | ScalarDB Tx内で集約更新とOutboxを書き込む |
| 集約の状態を自由に書き換える | finalクラスと不変集約 |

この改善は、リファクタリングの効果測定としてかなり大きいです。

なぜなら、コード量やファイル数だけを見ても、保守性が上がったかどうかは分かりません。むしろマイクロサービス化によってファイル数やサービス数は増えます。それでも保守しやすくなったと言えるのは、変更してよい場所と変更してはいけない場所が、構造として分かれるからです。


### レガシー構造からの変化

#### God Serviceから境界コンテキストへ

現状分析では、`OrderService`が976行のGod Serviceになっていました。

このクラスは、注文CRUDだけでなく、統計、カート計算、返品チェックなども抱えていました。さらに`CheckoutSaga`は557行、`ReturnSaga`は448行あり、複数データベース更新、外部副作用、補償処理がひとつのクラスに集中していました。

リファクタリング後は、責務が13サービスに分割されています。

| レガシー側の責務 | 改善後の配置 |
|---|---|
| 商品マスタ | catalog-service |
| 在庫引当・戻し | inventory-service |
| 注文作成・状態遷移 | order-service |
| 決済・返金 | payment-service |
| 会員・ポイント | loyalty-service |
| レシート | receipt-service |
| 返品 | return-service |
| チェックアウト全体の進行 | checkout-orchestrator |
| カート | cart-service |
| 認証・ユーザー管理 | identity-service |
| 監査ログ | audit-service |
| 集計・KPI | dashboard-service |
| 外部公開API | api-gateway |

これは、単にクラスを小さくしたという話ではありません。

各サービスが、自分のドメインモデル、データ、API、Dockerfile、テスト、CI設定を持つ単位になっています。実装編で見た通り、`services/`配下にはバックエンド13サービスと`pos-frontend`が配置され、Javaファイルはサービス境界ごとに分散しています。

レガシーの中心にあった`OrderService`という巨大な重力源がなくなり、業務上の境界に合わせて責務が配置され直した。ここが最初の大きな改善です。


#### 手書きSagaから観測可能なSagaへ

レガシーの`CheckoutSaga`と`ReturnSaga`では、Sagaの進行状況がコード上のローカルな処理に閉じていました。

処理が途中で失敗したとき、どこまで成功したのか、どの補償が必要なのか、補償が二重に走らないか、再試行すべきなのか、人間がコードとログを追いながら判断する必要がありました。

設計フェーズでは、この問題に対して、ScalarDBで扱えるPure Tx領域と、外部決済SaaSや通知のような副作用領域を分けました。実装フェーズでは、`shared/saga`、Saga状態、Saga Step、Timeout Evaluator、Leader Lock、Outboxイベントとして形にしています。

これにより、Sagaは巨大な`try-catch`ではなく、観測可能な業務プロセスになります。

![refactoring-saga](/images/legacy-refactoring-nexus-scalardb/refactoring-saga.png)
*観測可能なSaga*

| 観点 | レガシー | 改善後 |
|---|---|---|
| 進行状態 | クラス内の処理フローに埋もれる | saga_stateやStepとして管理 |
| 補償 | 手書きの分岐と例外処理 | 補償イベントと状態遷移として追跡 |
| タイムアウト | 判断しづらい | Timeout Evaluatorで検出 |
| 多重実行 | 防止が難しい | ScalarDB分散リーダー選出で制御 |
| 外部副作用 | DB更新と混ざりやすい | Outbox ACL WorkerでTx外に隔離 |

特に、`Refund`と`Reverse`がコード上で区別されている点も重要です。

顧客都合の返金と、Saga補償としての取消は、似ているようで業務上の意味が違います。この違いは、`Payment.refund()`と`Payment.reverse()`、`PaymentRefundedEvent`と`PaymentReversedEvent`として表現されており、ユビキタス言語の改善としても重要です。


#### DAO直接依存からポート/アダプターへ

レガシーでは、ServiceやSagaがDAO、JdbcTemplate、複数DBを直接扱っていました。

この構造では、ビジネスルールをテストしたいだけでもDB接続やテーブル状態の準備が必要になります。また、DBアクセスの詳細が業務ロジックに混ざるため、ScalarDBへ移行するときの影響範囲も広くなります。

改善後は、全16リポジトリと5外部サービスポートで、ポート/アダプターパターンが使われています。

```text
domain
  XxxRepository

infrastructure
  ScalarDbXxxRepository
  JdbcXxxRepository
  RedisXxxRepository
  ExternalApiClient
```

ドメイン層は、ScalarDBの`Get`、`Put`、`Scan`を知りません。RedisやJDBCも知りません。外部決済サービスも`PaymentPort`の向こう側に隠れます。

改善後の構造では、以下が実測確認されています。

| 検証項目 | 結果 |
|---|---|
| クロスサービスのドメインモデル直接import | ゼロ |
| ScalarDB型のdomain層露出 | ゼロ |
| shared/commonから特定サービスへの依存 | ゼロ |
| 循環依存 | ゼロ |

ここは効果測定として非常に分かりやすい部分です。

以前は、依存があるかどうかを読む人間の感覚で判断していました。改善後は、依存してはいけない方向にコードが伸びていないことを、構造と分析結果で確認できます。


### アーキテクチャ品質の改善

#### 4層レイヤリングが全サービスに揃った

リファクタリング後のサービスは、基本的に以下の4層で構成されています。

![four-layer-architecture](/images/legacy-refactoring-nexus-scalardb/four-layer-architecture.png)

```text
domain
application
infrastructure
presentation
```

この4層レイヤリングは全13サービスに一貫適用され、アーキテクチャ層は5/5と評価されています。

それぞれの役割は明確です。

| 層 | 役割 |
|---|---|
| domain | 集約、値オブジェクト、状態遷移、ビジネスルール |
| application | ユースケース調整、トランザクション境界、Sagaステップ調整 |
| infrastructure | ScalarDB、Redis、JDBC、外部APIクライアント |
| presentation | Controller、HTTP入出力、ルーティング |

レガシーでは、Controller、Service、DAO、Sagaの境界が曖昧で、ビジネスルールがServiceやSagaに集中していました。改善後は、`Order.cancel()`、`Payment.refund()`、`Stock.allocate()`のようなルールがdomain層の集約メソッドに閉じています。

この構成では、Controllerにロジックを書く余地が小さくなります。Application Serviceも、ドメインルールを自分で判断するのではなく、集約に依頼します。

つまり、設計の良し悪しがレビュー担当者の注意力だけに依存しなくなっています。


#### 集約設計とScalarDB Tx境界が対応した

今回のリファクタリングでは、集約設計が単なるDDDの形だけで終わっていません。

重要なのは、集約境界とScalarDBトランザクション境界が対応していることです。

`Order`、`Payment`、`Stock`は不変集約として設計され、状態変更は新しいインスタンスを返す形になっています。また、1 ScalarDB Tx = 1集約の書き込み + Outboxエントリというルールも全サービスに徹底されています。

この効果は大きいです。

レガシーでは、複数DBを跨いだ更新が手書きSagaの中にあり、途中失敗時に半端な状態が残るリスクがありました。改善後は、1つの業務変更でどこまでを原子的に扱うのかが明確になっています。

```text
ScalarDB Tx内
  集約を更新する
  関連エンティティを更新する
  Outboxエントリを書く

ScalarDB Tx外
  Polling Publisherがイベントを発行する
  外部API Workerが副作用を実行する
```

この分離により、DB内で保証できる一貫性と、外部副作用として追跡すべき処理が混ざらなくなりました。

設計・実装編で見た通り、ScalarDBを導入してもSagaが不要になるわけではありません。ScalarDBで消えるのは、MySQLとPostgreSQLを跨いだDB更新の不整合です。一方で、外部決済SaaS、通知、レシート印字のような副作用は、OutboxとSagaで扱い続ける必要があります。

今回の改善は、その境界をコード構造として表現できた点にあります。


#### 境界コンテキストがコード、データ、通信で分離された

設計フェーズでは、Catalog、Inventory、Order、Payment、Loyalty、Return、Receipt、Audit、Dashboardなどの境界コンテキストを定義しました。

改善後の評価では、この境界がコード、データ、通信の3層で確認されています。

| 分離の種類 | 実装 |
|---|---|
| コード | 各サービスは`shared/*`のみに依存 |
| データ | ScalarDB namespace単位で分離 |
| 通信 | Outbox + Polling Publisher経由で統合 |

特に、ドメインモデルの直接共有がゼロである点は大きな成果です。

マイクロサービス化でよく起きる失敗に、サービスは分かれているが、共通モデルが巨大化して結局すべてがつながる、というものがあります。今回の構成では、`shared/common`は`Money`、`Quantity`、`DomainEvent`、`PosException`のようなドメインプリミティブに抑えられています。

`shared/common`のMMIは96%で、全モジュールの中でも最も高い評価になっています。

これは、共通化の範囲が適切だったことを示しています。便利だから何でも共有するのではなく、共有してよいものだけを共有する。その制約が、境界コンテキストの独立性を守っています。


### データ整合性とイベント連携の改善

#### Dual-WriteリスクがOutboxで抑えられた

レガシーシステムでは、業務データ更新、監査ログ、通知、Dashboard更新が別々の処理として扱われると、どれか一部だけ成功するリスクがありました。

たとえば、注文データは更新されたが監査ログが残らない、決済は成功したがDashboardに反映されない、イベント通知だけ失敗した、という状態です。

改善後は、28個のドメインイベントがOutboxパターンで扱われています。

| 発行元 | 主なイベント |
|---|---|
| Order | OrderPlacedEvent、OrderCancelledEvent、OrderCompletedEvent |
| Inventory | StockAllocatedEvent、StockCommittedEvent、StockRestoredEvent、LowStockDetectedEvent |
| Payment | PaymentChargedEvent、PaymentRefundedEvent、PaymentReversedEvent |
| Loyalty | MemberRegisteredEvent、PointsAwardedEvent、PointsReversedEvent |
| Return | ReturnRequestedEvent、ReturnCompletedEvent |
| Receipt | ReceiptIssuedEvent |

集約更新とOutboxエントリは同じScalarDBトランザクションで書き込まれます。

これにより、データは更新されたがイベントが発行対象として記録されていない、という状態を防げます。イベントの実配送はTx外で行われますが、少なくとも配送すべきイベントがDBに残るため、再送、監査、リプレイが可能になります。

この改善は、単に非同期化したという話ではありません。

むしろ、非同期処理にしたうえで、失われない形にしたことが重要です。


#### Dashboard集計がWrite Modelから切り離された

設計レビューでは、Dashboard集計が大きな論点になっていました。

初回設計では、ScalarDB Standardの制約を考えると、`GROUP BY`や`SUM`をそのままWrite Modelに対して実行する設計は成立しない、という指摘がありました。

その後、設計はCQRS Read Modelへ修正され、実装でも`dashboard-service`は独立したRead Modelとして扱われています。

この改善によって、注文や決済のWrite Modelは業務更新に集中できます。一方、DashboardはOutboxから投影されたRead DBを使い、集計に適した形でクエリできます。

| 観点 | レガシー | 改善後 |
|---|---|---|
| 集計ロジック | `OrderService`周辺に混在 | dashboard-serviceへ分離 |
| データ取得 | 業務DBに直接問い合わせ | Read Modelを参照 |
| ScalarDB制約 | 集計SQLとの相性が悪い | PostgreSQL Read DBで集計 |
| 障害影響 | 集計負荷が業務更新に影響 | Write ModelとRead Modelを分離 |

これは、レビューでFAILになった指摘が、そのまま設計改善と実装改善につながった良い例です。

リファクタリングの効果は、静的なコード構造だけではありません。実行時の負荷分離、障害時の影響範囲、運用時の再構築可能性にも現れます。


#### ScalarDB統合がルールとして定着した

ScalarDB Enterprise Standardの重要原則も、構造的に強制される形になっています。

特に以下の点です。

| 原則 | 実装 |
|---|---|
| Tx内で外部APIを呼ばない | Outbox ACL WorkerでTx外に隔離 |
| 集約 = Tx境界 | 1 Tx = 1集約 + Outboxエントリ |
| Dual-Writeを防ぐ | 集約更新とOutboxを同一Txで書く |
| ScalarDB型をドメイン層に漏らさない | infrastructure層アダプターに封じ込め |
| OCC競合を扱う | Stock集約でjitter付きリトライ |

設計・実装編でも見た通り、ScalarDBは便利な魔法ではありません。使い方を間違えると、Tx内で外部APIを呼んだり、Scan制約を無視したり、OCC競合をそのまま500系エラーにしたりします。

今回の実装では、その落とし穴を設計と共通部品で封じています。

`shared/outbox`はTransactional Outboxだけに集中し、MMI86%と評価されています。`shared/saga`はSaga基底クラスやTimeout Evaluatorを提供し、ScalarDB分散リーダー選出に対応しています。さらに、`docs/solutions/`にはScalarDB Result API、Putの部分更新、Transaction Lifecycle、CommitConflictExceptionのリトライ方針などが蓄積されています。

つまり、ScalarDBの知識が個別サービスの中に散らばるのではなく、共通部品と学習記録に集まっています。


### 保守性とテスト容易性の改善

#### テスト対象を小さくできる

レガシー構造では、ビジネスロジックを検証したいだけでも、背後にあるMySQL、PostgreSQL、DAO、Saga、外部副作用を意識する必要がありました。

改善後は、ドメイン層とアプリケーション層がポートに依存しています。したがって、テストではScalarDBアダプターの代わりにスタブやモックを差し込めます。

これは、テストが速くなるというだけではありません。

業務ルールのテストと、ScalarDBアダプターのテストと、API Controllerのテストを分けられるようになります。

| テストしたいこと | 主な対象 |
|---|---|
| 状態遷移の正しさ | domainの集約 |
| ユースケースの流れ | application service |
| ScalarDBマッピング | infrastructure adapter |
| HTTP入出力 | presentation controller |
| Sagaの補償 | shared/sagaとorchestrator |
| イベント発行 | shared/outbox |

テスト対象を小さくできると、失敗したときの原因も狭くなります。

以前は、チェックアウトのテストが落ちたときに、注文ロジック、在庫、ポイント、決済、DB、補償処理のどこが原因か切り分ける必要がありました。改善後は、各サービスと層ごとに責務が分かれているため、問題の所在を追いやすくなります。


#### 変更の影響範囲が読みやすくなった

リファクタリングの効果は、将来の変更でよく分かります。

たとえば、ポイント付与ルールを変更する場合、主な変更先は`loyalty-service`です。税計算や価格ルールを変更する場合は、対応するドメインモデルとサービスに閉じます。Dashboardに新しいKPIを追加する場合は、Write ModelではなくRead Model側の投影と集計を触ります。

レガシーでは、こうした変更が`OrderService`やSagaに吸い込まれがちでした。

改善後は、どの責務をどのサービスが持つかが明確です。

| 変更内容 | 主な変更先 |
|---|---|
| 商品価格やバーコード管理 | catalog-service |
| 在庫引当ルール | inventory-service |
| 注文状態遷移 | order-service |
| 決済取消と返金 | payment-service |
| ポイント付与率 | loyalty-service |
| 返品可能条件 | return-service |
| 監査ログ項目 | audit-service |
| KPI追加 | dashboard-service |

もちろん、マイクロサービス化すればすべての変更が単独サービスで完結するわけではありません。イベント契約やAPI契約の変更が必要になる場合もあります。

それでも、変更の起点が分かりやすくなり、影響範囲を設計上の境界に沿って調べられるようになったことは大きな改善です。


#### 新メンバーが迷いにくい

保守性は、コードを読む人にとっての地図の分かりやすさでもあります。

レガシーシステムでは、業務フローを理解するには`OrderService`、`CheckoutSaga`、`ReturnSaga`、DAO、複数DBスキーマを横断して読む必要がありました。しかも、どこまでが注文の責務で、どこからが在庫や決済の責務なのかがコード上で曖昧でした。

改善後は、最初に見るべき場所が分かります。

注文なら`order-service`、在庫なら`inventory-service`、決済なら`payment-service`です。各サービスの内部は4層に揃っているため、業務ルールを見たいならdomain、ユースケースを見たいならapplication、DB実装を見たいならinfrastructure、HTTP APIを見たいならpresentationを読めばよい。

これは、チーム開発で効きます。

人が増えるほど、暗黙知に頼った設計は崩れやすくなります。今回の構造では、何をどこに書くかが自然に誘導されるため、人数が増えてもレガシー化しにくい土台になります。


### 運用面の改善

#### 可観測性が設計後付けではなくなった

初回の設計レビューでは、HA/DRや可観測性の不足も大きな指摘でした。

v3レビューでは、Operations観点のHIGH課題が解消され、SLO、Burn Rateアラート、Golden Signals、ScalarDBダッシュボード、Runbookなどが追加されています。

可観測性も、今回の改善における重要な強みです。

| 観点 | 実装 |
|---|---|
| 分散トレーシング | OpenTelemetry |
| メトリクス | Micrometer + Prometheus |
| ログ | traceId/spanId付き構造化JSONログ |
| SLI/SLO | サービスごとに定義 |
| ダッシュボード | Grafana |
| デプロイ | Argo CD + Kustomize |
| カナリア | Argo Rollouts |
| 自動ロールバック | SLO違反検知と連動 |

レガシーリファクタリングでは、コード構造の改善だけに意識が寄りがちです。

しかし、実際に本番で使うには、どのサービスが遅いのか、どのSagaが詰まっているのか、ScalarDBの競合が増えていないか、Outboxの配送遅延が出ていないか、デプロイ後にSLOが悪化していないかを見られる必要があります。

今回の改善では、その観測点もアーキテクチャの一部として扱われています。


#### デプロイと切り戻しの前提ができた

13サービスになると、起動順序、設定、ヘルスチェック、デプロイ順序、切り戻しが重要になります。

実装編で見たように、実装ではDocker Compose、GitHub Actions、GitLabマルチレポ構成、Kubernetesマニフェスト、GitOpsまで含めて整備されています。

これにより、リファクタリング後のコードは、設計書上の理想構成ではなく、動かして検証できる構成に近づいています。

特に、Argo RolloutsとSLOベースの自動ロールバックが入っている点は、マイクロサービス化後のリスク低減として重要です。

サービスを分けると、変更単位は小さくなります。一方で、デプロイ対象は増えます。だからこそ、失敗したリリースを早く検知し、影響を限定し、戻せる仕組みが必要です。

設計レビューで運用リスクを拾い、実装フェーズでデプロイと可観測性に反映したことが、今回の改善効果を支えています。


### MMIスコアから見る改善の偏り

#### 高スコアモジュールが示していること

モジュール別のMMIを見ると、改善の偏りも分かります。

特に高いのは、以下のモジュールです。

| モジュール | MMI |
|---|---:|
| shared/common | 96% |
| shared/outbox | 86% |
| identity-service | 86% |
| cart-service | 86% |
| audit-service | 86% |
| shared/saga | 82% |
| shared/security | 82% |
| api-gateway | 82% |
| catalog-service | 82% |

`shared/common`が96%と高いのは、責務が絞られているからです。`Money`、`Quantity`、`DomainEvent`、`PosException`のような、複数サービスで使うが特定サービスに依存しない部品だけを持っています。

`audit-service`が86%なのも分かりやすいです。監査ログは横断的関心事ですが、他サービスを呼び出すのではなく、Outboxイベントを消費して構造化監査レコードを作る形になっています。つまり、横断的でありながら、結合を増やさない実装になっています。

`cart-service`もRedis上のエフェメラルなカート管理に特化しており、ScalarDBを必要としません。これは、すべてを同じ技術で統一するのではなく、責務に合った永続化方式を選べている例です。


#### 低めのスコアも失敗とは限らない

一方で、`checkout-orchestrator`は52%、`return-service`は56%と、他より低いスコアになっています。

ただし、これはアーキテクチャ欠陥ではなく、Sagaパターンの構造的複雑性を反映していると読むべきです。

Checkout Orchestratorは、在庫、注文、決済、ポイント、レシートなど複数サービスを調整する役割です。したがって、ポート依存が多くなるのは自然です。Return Serviceも、返品、在庫戻し、ポイント取消、返金などを扱うため、単純なCRUDサービスより複雑になります。

大事なのは、依存があること自体ではありません。

依存がポート経由で明示され、ドメインモデルを直接共有せず、Sagaの複雑性として隔離されていることです。

つまり、スコアを読むときは、数字だけで良い悪いを判断するのではなく、そのモジュールが担う責務と照らして見る必要があります。


### 効果測定として見えたこと

#### 改善されたリスク

ここまでの内容を、レガシー時点のリスクと改善後の状態で整理すると、以下のようになります。

| レガシー時点のリスク | 改善後の状態 |
|---|---|
| `OrderService`に責務が集中 | 13サービスへ責務分散 |
| 手書きSagaで補償が追跡しづらい | saga_state、Outbox、Timeout Evaluatorで観測可能 |
| MySQL/PostgreSQL跨ぎ更新が不安定 | ScalarDB TxでPure Tx領域を制御 |
| 外部副作用とDB更新が混ざる | Outbox ACL WorkerでTx外へ隔離 |
| Dashboard集計が業務DBに負荷をかける | CQRS Read Modelへ分離 |
| DAO/JdbcTemplateが業務ロジックに漏れる | ポート/アダプターで封じ込め |
| 他ドメインのモデルを直接参照する | クロスサービスのドメインモデル共有ゼロ |
| 監査ログやイベント欠落が起きうる | 28イベントをOutboxで原子的に記録 |
| 設計レビューで運用観点が不足 | SLO、Runbook、GitOps、Rolloutsを追加 |
| 実装知識が散逸する | `docs/solutions/`に蓄積 |

この表を見ると、リファクタリングの効果は、単に可読性が上がったというより、失敗の種類を減らしたことにあります。

特に大きいのは、以下の3つです。

- 責務の集中を減らした
- 一貫性を壊す経路を減らした
- 変更と運用の影響範囲を見えるようにした


#### 残っている注意点

もちろん、これでリファクタリングが完全に終わったわけではありません。設計レビューv3では、P1としてスキーマ整合やOutbox/Saga運用詳細、Dashboard Read DBのDR戦略など、まだ残っている課題も挙げられていました。

また、マイクロサービス化によって新しい複雑性も生まれます。

- サービス間契約の互換性管理
- イベントスキーマのバージョニング
- OutboxとProjectorの遅延監視
- Saga補償の運用Runbook
- ScalarDBのOCC競合監視
- Read Model再構築手順
- 複数チーム間の境界調整

ただし、これらは見えていない複雑性ではありません。

設計レビュー、docs/plans、docs/solutions、可観測性設計によって、複雑性が管理対象として表に出ています。ここがレガシー状態との大きな違いです。

レガシーの複雑性は、巨大なServiceやSagaの内部に埋もれていました。改善後の複雑性は、サービス境界、イベント、Saga、運用設計として名前が付いています。

名前が付いた複雑性は、測定し、レビューし、改善できます。

### この連載で見えてきたこと

この連載では、レガシーPOSシステムを題材にして、Nexus ArchitectとScalarDBを使ったモダナイゼーションを扱いました。全体を通して見えてきたのは、レガシーリファクタリングで重要なのは、いきなりコードをきれいに書き直すことではないという点です。まず必要なのは、今のシステムがどのような構造になっていて、どこに変更しづらさや壊れやすさがあるのかを理解することでした。

今回のPOSシステムでは、`OrderService`、`CheckoutSaga`、`ReturnSaga`に多くの責務が集まっていました。MySQLとPostgreSQLをまたぐ更新、手書きSaga、DAOへの直接依存、画面とAPIの混在などもあり、機能追加や障害対応のたびに影響範囲を読み解く必要がある構造になっていました。

この状態に対して、Nexus Architectは現状を可視化し、設計の論点を整理する役割を担いました。どのクラスに責務が集中しているのか。どの境界が崩れているのか。どのトランザクションが危険なのか。そうした問題を、人の感覚だけではなく、レポートとして確認できるようになりました。

一方で、分析だけではシステムは良くなりません。境界コンテキスト、ポート/アダプター、ScalarDB、Outbox、Saga、CQRSリードモデル、可観測性などを使いながら、複雑性をどこに置くのかを設計し直す必要がありました。その結果として、責務は13個のSpring Bootマイクロサービスへ分かれ、DBアクセスはポートの背後に隠れ、外部副作用はOutboxやSagaとして扱われるようになりました。

ここで大切なのは、サービス数が増えたこと自体ではありません。変更してよい場所と、守るべき境界が見えるようになったことです。レガシーの複雑性をなくすことはできません。しかし、複雑性に名前を付け、設計に落とし込み、実装と運用の中で扱える形に変えることはできます。この連載全体を通して見てきたのは、そのための進め方だったと思います。


### 大事だったこと

今回の取り組みで大事だったのは、最初から完璧なマイクロサービスを作ることではありません。大事なのは、今の構造を正しく見ることです。

レガシーシステムでは、問題がコードの中に埋もれがちです。巨大なService、例外を握りつぶす補償処理、複数DBへの直接更新、画面に混ざったビジネスロジックなどは、日々の開発の中では見慣れたものになってしまいます。

しかし、一度構造として可視化すると、どこから直すべきかが見えてきます。今回でいえば、最初に直すべきだったのは、細かな命名や見た目の整理ではありませんでした。

責務の集中をほどくこと。データ一貫性を壊す経路を減らすこと。外部副作用をトランザクションの外に出すこと。ドメイン層から技術詳細を追い出すこと。このように、変更に強い構造へ少しずつ近づけることが重要でした。


### Nexus ArchitectとScalarDBの役割

Nexus Architectは、設計を考えるための補助線として役立ちました。

現状分析、ドメイン整理、境界コンテキスト設計、ターゲットアーキテクチャ、リファクタリング計画、レビューまでを一連の流れとして扱えるため、作業が単発の改善で終わりにくくなります。特に、AIエージェントにただ実装を依頼するのではなく、分析、設計、実装、レビュー、効果測定という流れを持たせることが重要だと感じました。

ScalarDBは、分散したデータを扱ううえでの土台として役立ちました。

複数DBをまたぐ更新を、アプリケーション側の手書きSagaだけで守ろうとすると、どうしても補償処理や例外処理が複雑になります。今回の設計では、ScalarDBで扱うPure Tx領域と、OutboxやSagaで扱う副作用領域を分けることで、どこまでを強く一貫させ、どこからを非同期に扱うのかが明確になりました。この役割分担があることで、モダナイゼーションは単なるサービス分割ではなく、一貫性を保ちながら進める設計作業になります。


### 実務で始めるなら

実際のプロジェクトで同じことを始める場合、最初から全体を作り直す必要はありません。まずは、現状分析だけでも十分に価値があります。どのクラスが大きいのか、どのモジュールが強く結合しているのか、どこでDB更新と外部副作用が混ざっているのかを確認します。

次に、変更頻度が高い領域や障害時の影響が大きい領域を一つ選びます。

その領域だけでも、責務を分ける、リポジトリインターフェースを作る、ドメイン層からDB実装を隠す、イベント発行をOutboxに寄せる、といった改善を始められます。

いきなりマイクロサービス化しなくてもよいと思います。まずはモノリスの中で境界を作る。次にデータアクセスを隠す。そのあと必要に応じてScalarDBを導入する。さらに必要になったらサービスとして切り出す。この順番のほうが、安全に進めやすいです。

### おわりに

レガシーリファクタリングは、古いコードをきれいにする作業だけではありません。今後の変更を受け止められる構造に変えていく作業です。

今回のPOSシステムでは、`OrderService`や手書きSagaに集まっていた複雑性を、境界コンテキスト、ポート/アダプター、ScalarDB、Outbox、Saga、CQRSリードモデル、運用設計へ分散させました。

複雑性が消えたわけではありません。ただし、見えない場所に埋もれていた複雑性に名前を付け、測定し、レビューし、改善できる形にできました。ここが一番大きな変化だと思います。
この連載の内容が、既存システムを前にして、どこから手を付ければよいか分からないと感じている方の参考になれば幸いです。

まずは小さく分析する。次に境界を見つける。そして、壊れにくい形へ少しずつ変えていく。その積み重ねが、現実的なモダナイゼーションの第一歩になると思います。

## 用語解説

### 効果測定
リファクタリング前後で構造、依存関係、運用性、データ一貫性、変更容易性がどう変わったかを確認することです。

### 副作用境界
外部決済、通知、監査連携など、DBトランザクションだけでは戻せない処理をどこで扱うかを示す境界です。

### モジュラモノリス
一つのアプリケーションとして動かしながら、内部を明確なモジュール境界で分ける設計です。

### 段階的移行
全体を一度に作り直すのではなく、分析、境界整理、データアクセス分離、ScalarDB導入、サービス分割のように順番に進める移行方法です。

### CQRS
Command Query Responsibility Segregationの略で、更新系と参照系の責務を分ける考え方です。Dashboard Read Modelの設計で重要になります。
