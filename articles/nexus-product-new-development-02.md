## Nexus Architectとの壁打ちをどう使ったか

:::message
RADARは、最初から完成した要求をNexus Architectへ渡して作ったものではありません。業務上の曖昧さを、対話と成果物の更新によって段階的に減らしました。
:::

### Nexus Architectの役割

本連載でいうNexus Architectは、プロダクト構想とシステムアーキテクチャ設計を支援するAIエージェント用のスキル・ワークフロー群です。

RADARでは、大きく2つのパイプラインを使いました。

| パイプライン | 主な対象 |
| :--- | :--- |
| `product:*` | Vision、成功指標、仮説、ペルソナ、UI、機能、MVP |
| `architect:*` | 要求、コード調査、DDD評価、境界、データ、API、運用設計 |

Productパイプラインで **何を、誰のために作るか** を整理し、MVPで価値を検証したあと、Architectパイプラインで **どう本番運用できる構造へするか** を設計しました。

ここで登場する`product:*`、`architect:*`、`/goal`などは、Claude CodeやCodexの標準コマンドではなく、RADAR開発時に利用したプラグイン側のワークフローです。Nexus Architect自体の位置づけや導入の前提は、 **[Nexus Architectとは何か？](https://zenn.dev/hako_hako/books/legacy-refactoring-nexus-scalardb/viewer/02-what-is-nexus-architect)** でも解説しています。

本連載では特定バージョンのコマンドリファレンスではなく、実際に生成された`docs/design-history/`を正として開発の流れを説明します。

### 最初の入力

起点となった情報は、巨大な要求仕様書ではありませんでした。

```text
Googleスプレッドシートで管理している商談・案件をアプリにしたい

中核にしたい機能
- 商談ステータス管理
- アサイン状況の可視化
- 遅延リスク管理
- 仮アサイン
```

ここからNexus Architectとの壁打ちで、対象ユーザー、価値、成功指標、やらないこと、検証方法を決めていきました。

### 対話型で進めた理由

新規プロダクトでは、AIが自動で決めると危険な論点があります。

- 自社利用とSaaS化のどちらを先にするか
- PMと営業のどちらをプライマリペルソナにするか
- 仮アサインは本当に差別化点なのか
- データ移行を初期スコープへ含めるか
- MVPの検証前に本番実装へ進むか
- レビューで基準を満たさなかったあと、どこまで直して実装へ入るか

RADARでは、AIエージェントが候補と推奨理由を出し、ユーザーが節目で選ぶ形を取りました。

```text
現状と未決事項を整理
  ↓
選択肢とトレードオフを提示
  ↓
ユーザーが判断
  ↓
判断を設計書へ記録
  ↓
次のパイプラインへ渡す
```

![AIとの壁打ちを成果物へ変える流れ](/images/nexus-product-new-development/chapter2-collaboration-pipeline.png)
_AIが候補を生成し、人間が節目で判断し、その決定をProduct・Architectパイプラインと設計履歴へ渡す_

### 会話を成果物へ変える

壁打ちを会話だけで終わらせないことも重要でした。

たとえば、 **既存データは移行しない** という短い判断は、次の成果物へ反映されました。

- **「既存データの移行」** を初回リリースの対象外へ変更
- それに伴い、 **「既存データを移行できる」** という仮説も検証対象から除外
- APIからインポート機能を除外
- データ移行計画とロールバック設計を初期範囲から除外

一つの判断が、スコープ、仮説、データ、API、リリース計画へ伝播しています。

![1つの判断を後続成果物へ反映する](/images/nexus-product-new-development/chapter2-decision-propagation.png)
_**「既存データは移行しない」** という判断を、スコープ・仮説・API・初期リリースへ反映する_

### 自動化と人間の判断を分ける

長い設計・実装では、AIエージェントに継続して作業させる場面もありました。一方、環境変更、外部サービス登録、スコープ変更、レビューを打ち切る判断は人間が行いました。

自動化するのは、決めた方針に沿った調査、文書化、実装、テストです。自動化しないのは、事業・業務・権限に関わる選択です。

この境界を持つことで、AIエージェントを単なるコード生成器ではなく、設計判断を前へ進める協働相手として使えます。

RADARでは、短い業務課題を起点にAIとの対話で選択肢を広げ、人間の判断を企画から設計・実装まで引き継ぎました。

## 壁打ちからプロダクトの方向性を固める

:::message
Productパイプラインの前半では、機能一覧を作る前に、Vision、利用者、価値、判断原則を言語化しました。
:::

### Visionを先に置く

RADARのVisionは、次のように整理されました。

> 商談から案件完了までの状態とアサインをリアルタイムに可視化し、誰が見ても **今どうなっているか** が一目でわかる組織をつくる。

この文章には、単なる案件台帳ではなく、商談とアサインを同じ流れで扱う意図が含まれています。

また、意思決定の原則として次の3点を置きました。

| 原則 | 意味 |
| :--- | :--- |
| 正確性を優先する | 見やすさのために受注状態や重複判定を曖昧にしない |
| **空いているか** に即答する | アサイン情報を探し回らせない |
| 確定と仮を区別する | UIとデータの両方で混同させない |

後の実装で、PostgreSQL排他制約や **破線＋仮ラベル** が採用されたのは、この段階の原則があったためです。

### Productパイプラインの実行順

RADARでは、方向性を一度に生成せず、次の順序で成果物を積み上げました。

```text
define-vision
  → define-success-metrics
  → research-landscape
  → design-revenue
  → define-scope
  → validate-assumptions
  → generate-persona
  → map-journey
  → design-positioning
  → create-domain-story
  → design-system
  → generate-ui-mock
  → define-features
  → define-data-model
  → generate-frontend
```

各段階の出力が次の入力になります。たとえばVisionの **確定と仮を区別する** はデザインシステムへ、ペルソナの判断場面はドメインストーリーとUIモックへ引き継がれました。

### 自社利用を最初の市場にする

将来的なSaaS化は候補に残しつつ、最初の利用先は自社としました。

この判断により、初期設計では次を選べます。

- 単一組織を前提にする
- Google Workspaceを認証基盤にする
- 30名程度までの利用を最初の目安にする
- テナント分離や課金をまだ実装しない

将来の可能性を捨てず、現在必要な複雑さだけを持つ方針です。

### 仮アサインを差別化点として扱う

競合調査では、SFA/CRMは商談管理に強い一方、人員アサインは中心ではありませんでした。リソース管理製品はアサインに強い一方、商談の受注確度とは分かれています。

RADARは、この間にある業務を狙いました。

```text
商談の受注確度
        ×
人員の空き・アサイン計画
        ↓
受注前から仮に人員を押さえる
```

調査した中ではFloatに仮割当て相当の考え方がありましたが、商談管理とは統合されていませんでした。このため、商談と仮アサインを同じデータモデルで扱うことを、最有力の差別化点としました。

### ペルソナを選ぶ

プライマリペルソナは、PM/リーダーの田中さんです。

田中さんが必要なのは、詳細な営業分析ではなく、次の問いへの答えです。

- この商談が受注した場合、誰を割り当てられるか
- そのメンバーはいつ空くか
- 仮アサインと正式アサインはどう違うか
- 遅延しそうな案件へ何をすべきか

セカンダリペルソナとして、商談状態を更新する営業の佐藤さんを置きました。

### North Star Metricを決める

成功指標の中心には、 **アサイン意思決定の即日確定率** を置きました。

これは、新規または見直しが必要な商談・案件について、担当アサインをその日のうちに決定・記録できた割合です。

入力指標には、週次アクティブ利用率、アサイン情報の鮮度、仮アサイン活用率、リスク対応リードタイムを置きました。誤アサイン・重複アサイン件数はガードレールです。

この時点では、現行のスプレッドシート運用を測った基準値がなく、多くの目標値は未定でした。AIがもっともらしい数値を埋めるのではなく、リリース後の実測で決める項目として残しました。

![Visionからプロダクトの方向性を固める](/images/nexus-product-new-development/chapter2-product-direction.png)
_Visionから判断原則、差別化点、最初の利用者、North Star Metricへつなぐ_

機能を考える前にVisionと判断原則を定め、自社利用と仮アサインに焦点を絞ったうえで、成果指標を **「アサイン意思決定の即日確定率」** としました。

## 仮説・成功指標・スコープをつなぐ

:::message
RADARでは、機能の優先順位だけでなく、何が起きたら方針を見直すかを仮説ごとに定義しました。
:::

### 必要な機能を並べるだけでは足りない

Productパイプラインでは、4つの中核機能を初回リリースに必要なものとしました。

| 初回リリースで扱う機能 |
| :--- |
| 商談ステータスの管理 |
| アサイン状況の可視化 |
| 遅延リスクの管理 |
| 受注前の仮アサイン |

このほか、基本的な登録・参照・更新・削除と認証・権限も必要です。

ただし、最終的に必要であることと、最初からすべて本番品質で作ることは同じではありません。投資する順序を決めるために、仮説と検証基準を用意しました。

### 外れたら企画全体を見直す仮説

最初に重視したのが、 **「専用アプリがスプレッドシートより優先して使われるか」** という仮説です。

> 専用アプリを作っても、利用者はGoogleスプレッドシートを優先して使い続けるのではないか。

この仮説が崩れると、画面やアーキテクチャをどれだけ作っても意味がありません。

検証方法は、営業とPM数名にMVPとスプレッドシートを1〜2週間併用してもらい、主にどちらを使ったかを構造化ヒアリングで確認することです。

方針を見直す基準も事前に置きました。

> 対象メンバーの過半数が、2週間後もスプレッドシートを主として使っていると回答したら、商談ステータス管理とアサイン可視化のUIまたは情報設計を見直す。

### 差別化の核となる仮説

次に置いたのが、 **「受注前の仮アサインが実際の商談で使われるか」** という仮説です。

> 受注前に人員を仮押さえする業務が実際にあり、仮アサイン機能が使われるのではないか。

当初は、実機能を作る前にUIモックを見せ、 **仮アサインしたい進行中商談があるか** をPM/リーダーへ尋ねる方法を考えました。

見直しの基準は、対象者の半数以上が **該当する商談が思いつかない** と回答することです。その場合は、仮アサインの想定シナリオ自体を見直します。

### 未検証を未検証のまま残す

すべての仮説を確認できたわけではありません。

| 確かめたいこと | 状態 |
| :--- | :--- |
| スプレッドシートよりアプリを優先する | 確認済み |
| 仮アサインが使われる | 確認済み |
| 既存データを移行できる | 対象外 |
| 調整時間が短縮する | 未検証 |
| 技術的に実装できる | 確認済み |
| 遅延を早期検知できる | 未検証 |

未検証の項目を確認済みとして扱わないことは重要です。現在の成果物でも、定量効果とリスク検知の実効性は残課題として記録されています。

### IDで判断をつなぐ

Vision、指標、スコープ、仮説にはIDが付いています。

```text
VIS-009 確定と仮を区別する
  ├─ SCP-004 仮アサイン
  ├─ NSM-004 仮アサイン活用率
  └─ ASM-002 仮アサインが使われるか
```

このつながりがあると、後で仕様やコードを変えたとき、 **どの価値仮説へ影響する変更か** を追いやすくなります。

![仮説・成功指標・スコープのトレーサビリティ](/images/nexus-product-new-development/chapter2-validation-traceability.png)
_判断原則・機能・成果指標・仮説を管理IDで接続し、確認済み・対象外・未検証を区別して残す_

必要な機能と実装順序を分け、各仮説の検証方法と見直し基準を先に決めたうえで、未検証の項目もそのまま追跡できるようにしました。

## ペルソナ・UIモック・デザインシステムを作る

:::message
方向性が固まったあと、Productパイプラインは業務ストーリー、UIモック、機能一覧、データモデルへ進みました。
:::

### ペルソナを業務ストーリーへ変える

ペルソナは、プロフィールを作ることが目的ではありません。どの場面で、誰が、何を判断するかを設計へ渡すために使います。

RADARでは、4つのドメインストーリーを作りました。

- PMが空きメンバーを探す
- PMが進行中商談へ仮アサインする
- PMが遅延リスクを確認して対応する
- 営業が商談ステータスを更新する

このストーリーが、後の画面とAPIの単位になります。

![ペルソナを業務ストーリーへ変える](/images/nexus-product-new-development/chapter2-persona-stories.png)
_2つのproto-personaを、誰が何を判断するかを表す4つのドメインストーリーへ変換する_

### 10操作画面のUIモック

Productパイプラインでは、4ストーリーに対応する10枚の操作画面をmid-fidelityモックとして生成しました。ストーリーごとのインデックス4枚と全体インデックスを含めると、`ui-mocks/`には15個のHTMLファイルがあります。

最重要のSTORY-002は、次の5画面です。

```text
商談詳細
  ↓
仮アサイン入力
  ↓
仮アサイン確認
  ↓
受注確認
  ↓
正式化結果
```

この時点では、本番の技術スタックよりも、業務上必要な情報と操作順序を確認しています。

### UIモックから機能とデータを抽出する

画面を作ったあと、19の機能と8つのエンティティを抽出しました。エンティティのうち6つは画面やフォームから明示的に抽出し、状態変更履歴の2つは機能とデータのCRUDマトリクスから暗黙的に検出しています。

画面だけを先に作ると、見た目に必要なフィールドへ設計が偏ります。そこで、ドメインストーリー、機能、データを相互に確認しました。

たとえば仮アサインには、次のデータが必要になります。

- 対象商談
- メンバー
- 仮/正式の種別
- 開始日と終了日
- 仮アサインの理由やメモ
- 正式化日時
- 状態変更履歴

後の本番実装では、案件リーダー、契約形態、月額単価、プロパー/BPなど、実利用で必要になった情報が追加されています。

![最重要フローをUI・機能・データへ落とす](/images/nexus-product-new-development/chapter2-story002-artifacts.png)
_STORY-002の5画面から、19機能と8エンティティを相互に確認する_

### デザイン原則をコードより先に決める

確定情報と仮情報を色だけで区別しないことを、デザインシステムの必須ルールにしました。

この判断には、2つの理由があります。

1. 色覚や表示環境に依存せず状態を伝えるため
2. 業務上、確定と仮の取り違えが実害につながるため

そのため、状態色に加え、ラベルと枠線を併用します。このルールは現在の`AssignmentCard`や`StatusBadge`にも残っています。

### 生成物を完成品だと思わない

Productパイプラインは、UIモック、機能一覧、データモデルを短時間でそろえました。しかし、この時点の成果物は仮説を形にしたものです。

操作画面が10枚あることも、機能が19個あることも、利用者に価値がある証明にはなりません。次に必要なのは、最小限の実働MVPを使った検証です。

ペルソナの業務を4つのストーリーと10枚の画面へ落とし込み、UI・機能・データを整合させながら、状態を色だけに頼らず伝える原則まで定めました。
