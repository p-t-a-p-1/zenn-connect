## コンシェルジュMVPを作って仮説を確かめる

:::message
本番のSpring BootとNext.jsへ進む前に、Hono、SQLite、React、Viteで使い捨てのコンシェルジュMVPを作りました。
:::

### MVPの目的

MVPで確かめたかったのは、本番アーキテクチャの妥当性ではありません。

- 商談状態をスプレッドシートより確認しやすいか
- 誰がいつ空くかを一覧できるか
- 仮アサインという業務概念が実際に使われるか
- PM/リーダーが日常の判断へ利用できるか

このため、素早く動かせる構成を選びました。

| 領域 | MVP |
| :--- | :--- |
| Backend | Hono |
| Database | SQLite |
| Frontend | React + Vite |

### 最初は検証サブセットから始める

初期のMVPは、SCP-001の商談ステータス管理と、SCP-002のアサイン可視化を中心に作りました。

その後、ユーザーの明示的な判断で、SCP-003の遅延リスクとSCP-004の仮アサインもMVPへ追加しました。

ここには注意点があります。当初の計画では、仮アサインはモックとヒアリングで仮説を確かめてから本実装する想定でした。実際には、実検証を待たずMVP実装へ進んでいます。

これは計画通りではありませんが、意思決定履歴にはその事実が残されています。AI駆動開発では、きれいな後付けストーリーにせず、計画から外れた判断も記録することが重要です。

### MVPにも業務トランザクションを持たせる

使い捨てMVPでも、仮アサインから正式アサインへの切り替えは、複数更新をまとめて扱う必要がありました。

```text
Dealを受注へ更新
  +
紐づく仮アサインを正式化
  +
履歴を保存
```

MVPではSQLiteのトランザクションで実現しました。このコード自体は本番へ移植しませんでしたが、 **どこまでを一つの整合性境界にするか** という知識は本番設計へ引き継がれました。

### 動作確認とアーカイブ

MVPは型チェック、ビルド、PlaywrightによるE2E動作確認まで実施しました。

検証後、MVPは本番コードへ昇格させず、`docs/concierge-mvp-archive/`へ移しました。

```text
MVPから引き継いだもの
- 使われた業務フロー
- 必要な画面と情報
- 仮アサインの状態遷移
- トランザクション境界の知識

引き継がなかったもの
- Hono/SQLiteの技術構成
- 単一ファイルに集中した責務
- 認証なしの前提
- 本番向けでないエラー処理
```

![MVPからコードではなく学びを渡す](/images/nexus-product-new-development/chapter3-mvp-learning-transfer.png)
_Hono・SQLiteのMVPを検証後にアーカイブし、コードではなく業務フローと整合性境界を本番設計へ渡す_

### この節のまとめ

- MVPは価値仮説を確かめるため、Hono、SQLite、React、Viteで構築しました。
- 当初の検証サブセットから、ユーザー判断で4中核機能へ拡張しました。
- MVPコードではなく、業務フローと整合性境界の知識を本番設計へ渡しました。
- 検証完了後のMVPは、削除せずアーカイブしました。

## 実運用検証とデータ移行をしない判断

:::message
MVPが動いたことと、プロダクトの価値が検証できたことを分けて扱います。RADARでは、実運用と構造化ヒアリングを検証ゲートにしました。
:::

### 仮判定と実検証を区別する

開発途中では、仮想的な会社像を使ったシナリオ推論も行いました。しかし、これは実検証ではありません。

設計履歴では、次のように区別されています。

1. 仮想シナリオによるASM-001/002の仮判定
2. MVP実装によるASM-005の技術的実現性確認
3. 実際の社内メンバーによる1〜2週間の利用
4. キル閾値を踏まえた構造化ヒアリング

AIが生成した利用シナリオだけでPassにせず、実際の利用まで待った点が重要です。

### ASM-001の結果

ASM-001は、 **専用アプリよりスプレッドシートが優先され続けるのではないか** という仮説です。

実運用後のヒアリングでは、 **対象者の過半数がスプレッドシートを主として使い続ける** というキル閾値へ抵触しませんでした。そのためPassとしました。

ただし、これは定量的な利用ログによる長期継続率の証明ではありません。1〜2週間の初期検証と構造化ヒアリングによるGo判断です。

### ASM-002の結果

ASM-002は、仮アサインに該当する実際の商談が存在するかを確認する仮説です。

実装済みの仮アサインを実際の商談で利用し、 **対象者の半数以上が該当商談を思いつかない** という閾値へ抵触しなかったためPassとしました。

ここでも、仮アサイン活用率や正式化率の継続計測は残っています。初期の価値仮説が通ったことと、定量的に効果を証明したことは分けます。

### データ移行をWon't-haveにする

実運用検証と並行して、既存スプレッドシートのデータを新システムへ移行しない判断をしました。

```text
SCP-007: 既存データ移行
Status: Won't-have
方針: ゼロから運用開始
```

この判断により、ASM-003のデータ移行仮説も対象外になりました。

データ移行には、列の意味、表記揺れ、色やコメント、欠損値、過去案件の扱いなど、多くの業務整理が必要です。初期リリースでその複雑さを抱えず、これからのデータを正しいモデルで蓄積する方針を選びました。

### Go判定の範囲

この時点のGoは、 **本番投資へ進んでよい** という意味です。 **すべての価値が証明済み** という意味ではありません。

未検証として残った代表例は次の2つです。

- ASM-004: アサイン調整時間が短縮するか
- ASM-006: 遅延リスクを手遅れになる前に検知できるか

残課題を明示したうえで、最重要2仮説と技術的実現性が通ったため、Architectパイプラインへ進みました。

![MVPの動作確認と価値検証を分ける](/images/nexus-product-new-development/chapter3-validation-gate.png)
_仮想シナリオ、技術確認、1〜2週間の実運用、構造化ヒアリングを分け、未検証を残したままGoの範囲を定める_

### この節のまとめ

- シナリオ推論、技術確認、実利用を別の検証段階として扱いました。
- ASM-001/002は、1〜2週間の実運用と事前定義した閾値に基づいてPassとしました。
- データ移行をWon't-haveにし、ゼロから運用を開始する方針を選びました。
- 定量効果とリスク検知実効性は、未検証項目として残しました。

## ProductからArchitectへ設計を引き継ぐ

:::message
MVP検証で価値仮説を確認したあと、Productパイプラインの成果物を要求ベースラインとしてArchitectパイプラインへ引き継ぎました。
:::

### 本番化はMVPの延長ではない

コンシェルジュMVPには、実際に使われた業務フローがあります。一方、本番運用に必要な認証、権限、監査、障害復旧、運用監視は備えていません。

そのため、MVPコードをそのまま整えて本番化するのではなく、要求定義から再開しました。

```text
Productパイプライン
  ├─ Vision・成功指標
  ├─ スコープ・仮説
  ├─ ペルソナ・UI
  └─ MVP検証結果
           ↓
Architectパイプライン
  ├─ 本番要求
  ├─ MVPコード調査
  ├─ MMI/DDD評価
  ├─ 境界コンテキスト再設計
  └─ データ・API・運用設計
```

### 引き継いだ要求ベースライン

`reports/00_core`から`04_quality`までの成果物を、Architect側の入力として扱いました。

特に重要な入力は次のとおりです。

- ASM-001/002がPassしたこと
- 仮アサインが中核価値であること
- データ移行を行わないこと
- 確定と仮を混同しないこと
- PM/リーダーと営業の業務ストーリー
- 本番で必要な認証、監査、通知、非機能要件

この引き継ぎにより、Architectパイプラインは一般的な業務アプリを設計するのではなく、検証済みのRADAR固有の価値を守る設計へ進めます。

実際の設計は、次の流れで進みました。

```text
architect:define-requirements
  → architect:investigate
  → architect:analyze
  → architect:evaluate-mmi / evaluate-ddd
  → architect:integrate-evaluations
  → architect:redesign
  → architect:design-microservices
  → architect:design-data-layer
  → architect:design-api
  → architect:review-*
```

コード調査と評価を挟んでから再設計するため、最初から理想アーキテクチャを当てはめる流れにはなっていません。

### 本番技術スタックを決める

要求定義で、次の技術スタックを選びました。

| 領域 | 技術 |
| :--- | :--- |
| Frontend | React / Next.js |
| Backend | Java 21 / Spring Boot |
| Database | PostgreSQL |
| Infrastructure | AWS |
| Authentication | Google Workspace OIDC |

MVPのHonoとSQLiteを採用し続けなかった理由は、MVPの失敗ではありません。学習用の実装と、継続運用する実装では最適化する対象が違うためです。

### モジュラーモノリスを選ぶ

設計パイプラインでは、マイクロサービス化の必要性も評価しました。

RADARの初期規模では、サービスごとのデプロイ、分散トランザクション、独立運用を持ち込む効果より、複雑さの方が大きいと判断しました。

そこで、単一のSpring Bootアプリケーション内で境界コンテキストをパッケージ分離する、モジュラーモノリスを採用しました。

同じ理由で、Kubernetesも初期構成では過剰投資と判断し、AWS ECS/Fargateを選びました。

### ScalarDBを採用しなかった理由

Nexus ArchitectにはScalarDB適用性を評価する流れもあります。しかしRADARは、単一PostgreSQL内のローカルトランザクションで中核処理を完結できます。

仮アサイン正式化は複数集約をまたぎますが、単一アプリ・単一DBの範囲です。分散トランザクション基盤を追加する必要はないと判断しました。

ツールが候補として扱える技術を、必ず採用するわけではありません。要求と運用規模に合わなければRejectすることも設計成果です。

![Productの学びをArchitectの本番要求へ渡す](/images/nexus-product-new-development/chapter3-product-to-architect.png)
_Product成果物を要求ベースラインとして渡し、MVPの延長ではなく本番技術スタックとモジュラーモノリスを選ぶ_

### この節のまとめ

- Productパイプラインの成果物を要求ベースラインとしてArchitectへ引き継ぎました。
- MVPコードの改修ではなく、本番要求から再設計しました。
- Spring Boot、Next.js、PostgreSQL、AWS、Google Workspace OIDCを選びました。
- 初期規模に合わせ、マイクロサービスではなくモジュラーモノリスを採用しました。

## MVPコードを調査しMMI・DDDで評価する

:::message
Architectパイプラインは、MVPを本番コードの雛形として扱うのではなく、業務知識と技術的負債の両方を含む調査対象として読みました。
:::

### まずコードを調査する

`architect:investigate`では、Hono + SQLiteのMVPを対象に、構造、依存、データアクセス、認証、テスト、ドメイン表現を確認しました。

MVPには、検証に必要な画面と業務操作がありました。一方、バックエンドの主要責務は少数のファイルへ集中していました。

```text
Controller
  + 入力検証
  + SQL実行
  + トランザクション
  + 業務ルール
  + レスポンス生成
```

短期間の検証には有効でも、本番機能を追加し続ける構造としては変更理由が集中しています。

### DDD移行準備度40.5点

MVP調査では、DDD移行準備度が40.5/100、Needs Improvementと評価されました。

この数値は、MVPの価値が低いという意味ではありません。業務上の概念は見えているものの、それらが集約、値オブジェクト、リポジトリ、ドメインサービスとして分離されていないことを示します。

たとえば、次の知識はMVPに存在しました。

- 商談には状態遷移がある
- アサインには仮と正式がある
- 正式化は複数更新をまとめる
- リスクには危険度と対応状態がある

しかし、その知識がルート処理やSQLの中に埋まっていました。

### MMI 66.0%、DDD 40.8%

Architectパイプラインでは、MMIとDDDを別の観点で評価しました。

| 評価 | 結果 | 読み方 |
| :--- | :--- | :--- |
| MMI | 66.0% / Moderate | 機能単位は見えるが責務境界が弱い |
| DDD | 40.8% / Weak | 集約、値、境界コンテキストへの明示化が不足 |

両評価を統合すると、根本原因は **単一ファイルへControllerとデータアクセスと業務ルールが直書きされていること** と整理されました。

### 調査で見つかった具体的なギャップ

評価では、構造だけでなく具体的な差分も見つかりました。

- 認証・認可が存在しない
- 重複アサインをDBで防げない
- リスク値が日本語と英語で二重表現される
- 権限マトリクスがない
- 自動テストがない
- 通知は実配信されない
- API契約がコードから独立していない

これらは、MVPで意図的に後回しにしたものと、実装中に生まれた技術的負債の両方を含みます。

### 数値を合否ではなく改善入力にする

40.5点や40.8%という評価だけを見て、MVPを作り直すことが目的ではありません。

評価結果は、次の設計作業へ変換されました。

```text
責務集中
  → 境界コンテキストとパッケージを再設計

重複防止不足
  → PostgreSQL排他制約

認証なし
  → BC-005と権限マトリクス

正式化の複雑さ
  → AssignmentFormalizationService
```

スコアを改善するためではなく、実装時に何を変えるかを決めるために評価を使いました。

![MMI・DDD評価を設計変更へ変換する](/images/nexus-product-new-development/chapter3-evaluation-to-design.png)
_責務集中という根本原因を、境界再設計、排他制約、認証、ドメインサービスの実装課題へ変換する_

### この節のまとめ

- MVPを、業務知識と技術的負債を含む調査対象として読みました。
- DDD移行準備度40.5、MMI 66.0%、DDD 40.8%と評価されました。
- 根本原因は、Controller、SQL、業務ルールの責務集中でした。
- 評価結果を、境界、DB制約、認証、ドメインサービスの設計へ変換しました。
