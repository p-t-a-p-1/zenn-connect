:::message
Productパイプラインの前半では、機能一覧を作る前に、Vision、利用者、価値、判断原則を言語化しました。
:::

## Visionを先に置く

RADARのVisionは、次のように整理されました。

> 商談から案件完了までの状態とアサインをリアルタイムに可視化し、誰が見ても **今どうなっているか** が一目でわかる組織をつくる。

この文章には、案件台帳に加えて、商談とアサインを同じ流れで扱う意図が含まれています。

また、意思決定の原則として次の3点を置きました。

| 原則 | 意味 |
| :--- | :--- |
| 正確性を優先する | 見やすさのために受注状態や重複判定を曖昧にしない |
| **空いているか** に即答する | アサイン情報を探し回らせない |
| 確定と仮を区別する | UIとデータの両方で混同させない |

後の実装で、PostgreSQL排他制約や **破線＋仮ラベル** が採用されたのは、この段階の原則があったためです。

## Productパイプラインの実行順

RADARでは、方向性を一度に生成せず、次の順序で成果物を積み上げました。

```text
define-vision（ビジョン定義）
  → define-success-metrics（成功指標の定義）
  → research-landscape（市場調査）
  → design-revenue（収益モデル設計）
  → define-scope（スコープ定義）
  → validate-assumptions（仮説検証）
  → generate-persona（ペルソナ生成）
  → map-journey（ジャーニーマップ作成）
  → design-positioning（ポジショニング設計）
  → create-domain-story（ドメインストーリー作成）
  → design-system（デザインシステム設計）
  → generate-ui-mock（UIモック生成）
  → define-features（機能定義）
  → define-data-model（データモデル定義）
  → generate-frontend（フロントエンド生成）
```

各段階の出力が次の入力になります。たとえばVisionの **確定と仮を区別する** はデザインシステムへ、ペルソナの判断場面はドメインストーリーとUIモックへ引き継がれました。

## 自社利用を最初の市場にする

将来的なSaaS化は候補に残しつつ、最初の利用先は自社としました。

この判断により、初期設計では次を選べます。

- 単一組織を前提にする
- Google Workspaceを認証基盤にする
- 30名程度までの利用を最初の目安にする
- テナント分離や課金をまだ実装しない

将来の可能性を捨てず、現在必要な複雑さだけを持つ方針です。

## 仮アサインを差別化点として扱う

| 用語 | 正式名称 | 説明 |
| :--- | :--- | :--- |
| SFA | Sales Force Automation | 営業活動の記録・追跡・自動化を担うシステム |
| CRM | Customer Relationship Management | 顧客関係を一元管理するシステム |

競合調査では、SFA/CRMは商談管理に強い一方、人員アサインは中心ではありませんでした。
リソース管理製品はアサインに強い一方、商談の受注確度とは分かれています。

RADARは、この間にある業務を狙いました。

```text
商談の受注確度
        ×
人員の空き・アサイン計画
        ↓
受注前から仮に人員を押さえる
```

調査した中では[Float](https://asana.com/ja/apps/float)に仮割当て相当の考え方がありましたが、商談管理とは統合されていませんでした。このため、商談と仮アサインを同じデータモデルで扱うことを、最有力の差別化点としました。

## ペルソナを選ぶ

プライマリペルソナは、PM/リーダーの田中さんです。

:::message alert
架空の人物です。実在の人物とは関係ありません。
:::

田中さんが必要なのは、次の問いへの答えです。詳細な営業分析は、その判断を支える材料として扱います。

- この商談が受注した場合、誰を割り当てられるか
- そのメンバーはいつ空くか
- 仮アサインと正式アサインはどう違うか
- 遅延しそうな案件へ何をすべきか

セカンダリペルソナとして、商談状態を更新する営業の佐藤さんを置きました。

## North Star Metricを決める

:::message
North Star Metric（ノーススターメトリック）とは、企業が長期的なビジネス成長を目指すために設定する最も重要な指標です。 
:::

成功指標の中心には、**アサイン意思決定の即日確定率**を置きました。

これは、新規または見直しが必要な商談・案件について、担当アサインをその日のうちに決定・記録できた割合です。

入力指標には、週次アクティブ利用率、アサイン情報の鮮度、仮アサイン活用率、リスク対応リードタイムを置きました。
誤アサイン・重複アサイン件数はガードレールです。

現時点では現行スプレッドシートの運用データによるベースラインが不足しており、多くの目標値は未定でした。
AIで仮の数値を埋めず、リリース後の実測で確定する項目として残しました。

このようにVision、利用者、差別化点、North Star Metricを先に定義することで、次章では単に機能一覧を作るのではなく、検証が必要な仮説に基づいてスコープを決めることができました。
