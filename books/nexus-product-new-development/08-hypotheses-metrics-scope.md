:::message
RADARでは、機能の優先順位だけでなく、何が起きたら方針を見直すかを仮説ごとに定義しました。
:::

## Mustを並べるだけでは足りない

Productパイプラインでは、4つの中核機能をMustとしました。

| ID | スコープ |
| :--- | :--- |
| SCP-001 | 商談ステータス管理 |
| SCP-002 | アサイン状況の可視化 |
| SCP-003 | 遅延リスク管理 |
| SCP-004 | 仮アサイン |

このほか、基本CRUDと認証・権限もMustです。

ただし、最終的にMustであることと、最初からすべて本番品質で作ることは同じではありません。投資順序を決めるために、仮説と検証ゲートを用意しました。

## 最大崩壊インパクトの仮説

最初に重視したのが`ASM-001`です。

> 専用アプリを作っても、利用者はGoogleスプレッドシートを優先して使い続けるのではないか。

この仮説が崩れると、画面やアーキテクチャをどれだけ作っても意味がありません。

検証方法は、営業とPM数名にMVPとスプレッドシートを1〜2週間併用してもらい、主にどちらを使ったかを構造化ヒアリングで確認することです。

キル閾値も事前に置きました。

> 対象メンバーの過半数が、2週間後もスプレッドシートを主として使っていると回答したら、SCP-001/002のUIまたは情報設計を見直す。

## 最大の差別化仮説

`ASM-002`は仮アサインに関する仮説です。

> 受注前に人員を仮押さえする業務が実際にあり、仮アサイン機能が使われるのではないか。

当初の検証案は、UIモックを見せて **仮アサインしたい進行中商談があるか** をPM/リーダーへ尋ねるWizard-of-Oz型でした。

キル閾値は、対象者の半数以上が **該当する商談が思いつかない** と回答することです。その場合は、仮アサインの想定シナリオ自体を見直します。

## 未検証を未検証のまま残す

すべての仮説が検証済みになったわけではありません。

| ID | 内容 | 状態 |
| :--- | :--- | :--- |
| ASM-001 | スプレッドシートよりアプリを優先する | 通過 |
| ASM-002 | 仮アサインが使われる | 通過 |
| ASM-003 | 既存データを移行できる | 対象外 |
| ASM-004 | 調整時間が短縮する | 未検証 |
| ASM-005 | 技術的に実装できる | 通過 |
| ASM-006 | 遅延を早期検知できる | 未検証 |

未検証の項目を検証済みとして扱わないことは重要です。現在の成果物でも、定量効果とリスク検知の実効性は残課題として記録されています。

## IDで判断をつなぐ

Vision、指標、スコープ、仮説にはIDが付いています。

```text
VIS-009 確定と仮を区別する
  ├─ SCP-004 仮アサイン
  ├─ NSM-004 仮アサイン活用率
  └─ ASM-002 仮アサインが使われるか
```

このつながりがあると、後で仕様やコードを変えたとき、 **どの価値仮説へ影響する変更か** を追いやすくなります。

仮説ごとに検証方法と見直し基準を置き、確認済みと未検証を分けて記録しました。次章では、検証対象を利用者の画面とデータへ落とし込みます。
