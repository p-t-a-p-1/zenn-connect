:::message
本番のSpring BootとNext.jsへ進む前に、Hono、SQLite、React、Viteで使い捨てのコンシェルジュMVPを作りました。
:::

## MVPの目的

MVPで確かめたかったのは、本番アーキテクチャの妥当性ではありません。

- 商談状態をスプレッドシートより確認しやすいか
- 誰がいつ空くかを一覧できるか
- 仮アサインという業務概念が実際に使われるか
- PM/リーダーが日常の判断へ利用できるか

このため、素早く動かせる構成を選びました。

| 領域 | MVP |
| :--- | :--- |
| Backend | Hono |
| Database | SQLite |
| Frontend | React + Vite |

## 最初は検証サブセットから始める

初期のMVPは、SCP-001の商談ステータス管理と、SCP-002のアサイン可視化を中心に作りました。

その後、ユーザーの明示的な判断で、SCP-003の遅延リスクとSCP-004の仮アサインもMVPへ追加しました。

ここには注意点があります。当初の計画では、仮アサインはモックとヒアリングで仮説を確かめてから本実装する想定でした。実際には、実検証を待たずMVP実装へ進んでいます。仮アサインが業務で使われるかどうかを、モックより動く実装で確かめる方が早いという判断でした。

これは計画通りではありませんが、意思決定履歴にはその事実が残されています。AI駆動開発では、きれいな後付けストーリーにせず、計画から外れた判断も記録することが重要です。

## MVPにも業務トランザクションを持たせる

使い捨てMVPでも、仮アサインから正式アサインへの切り替えは、複数更新をまとめて扱う必要がありました。

```text
Dealを受注へ更新
  +
紐づく仮アサインを正式化
  +
履歴を保存
```

MVPではSQLiteのトランザクションで実現しました。このコード自体は本番へ移植しませんでしたが、 **どこまでを一つの整合性境界にするか** という知識は本番設計へ引き継がれました。

## 動作確認とアーカイブ

MVPは型チェック、ビルド、PlaywrightによるE2E動作確認まで実施しました。

検証後、MVPは本番コードへ昇格させず、`docs/concierge-mvp-archive/`へ移しました。

```text
MVPから引き継いだもの
- 使われた業務フロー
- 必要な画面と情報
- 仮アサインの状態遷移
- トランザクション境界の知識

引き継がなかったもの
- Hono/SQLiteの技術構成
- 単一ファイルに集中した責務
- 認証なしの前提
- 本番向けでないエラー処理
```

MVPは、価値を確かめるための短命な実働環境として作り、コードではなく利用された業務フローと整合性境界を本番設計へ渡しました。次章では、MVPが動いたことと価値が確かめられたことを分けて検証します。
