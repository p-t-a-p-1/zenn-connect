:::message
本番設計を一通り作ったあと、Consistency、Data Integrity、Operations、Risk、Businessの5観点でレビューしました。
:::

## 5観点と重み

RADARのレビューは、次の5つです。

| 観点 | 重み | 主に確認すること |
| :--- | :---: | :--- |
| Consistency | 0.15 | 文書、API、用語、図の整合性 |
| Data Integrity | 0.25 | トランザクション、制約、同時実行 |
| Operations | 0.20 | 監視、デプロイ、復旧、運用手順 |
| Risk | 0.25 | セキュリティ、障害モード、依存リスク |
| Business | 0.15 | 価値、継続性、計画、要求との対応 |

初回の集約スコアは2.67で、判定はFAILでした。重大な課題は7件あり、すべて次工程へ進む前に解消すべき課題として扱いました。

## 初回レビューで不足していたもの

機能、ドメイン、APIの設計は進んでいました。一方、本番運用に必要な基盤設計が体系的に不足していました。

| 管理ID | 不足していた設計 |
| :--- | :--- |
| SYN-001 | ヘルスチェック |
| SYN-002 | アラート閾値とrunbook |
| SYN-003 | バックアップとRPO/RTO |
| SYN-004 | Multi-AZとフェイルオーバー |
| SYN-005 | シークレット管理 |
| SYN-006 | デプロイ戦略 |
| SYN-007 | OIDC障害時の挙動 |

MVPで価値を確認したあとでも、本番設計へ移るときにはこの空白を埋める必要があります。

## 4つの設計文書で重大課題を解消する

重大課題に対応するため、次の文書を追加しました。

- `security-design.md`
- `observability-design.md`
- `disaster-recovery-design.md`
- `infrastructure-architecture.md`

一つの文書が一つの重大課題に対応するのではありません。たとえばobservability設計が、ヘルスチェック、メトリクス、アラート、runbook参照をまとめて扱います。

## レビュー中に実バグを見つける

レビューは文章の採点だけではありません。実際に検証スクリプトを動かし、2件のバグを見つけました。

1. `auth-api.yaml`末尾へMarkdownが混入し、YAMLとしてパースできなかった
2. データ設計のコード例が、存在しない`DealStatus`列挙値を参照していた

どちらもレビューと同時に修正しています。

## 再レビューの結果

重大課題への対応後、同じ5観点で再レビューしました。

| 指標 | 初回 | 2回目 |
| :--- | :---: | :---: |
| aggregate | 2.67 | 3.62 |
| 重大な課題 | 7 | 0 |
| 重要な課題 | 26 | 18 |
| 判定 | FAIL | FAIL |

全観点が最低3.0を超え、集約スコアも合格基準の3.5へ到達しました。しかし、重要な課題を8件以下にする条件を満たさず、判定は基準未達のままでした。

判定だけを見ると変化がないように見えますが、重大な課題が0件になり、本番運用基盤の空白が埋まったことは大きな前進です。

## 重要な課題を設計へ反映する

運用基盤を設計すると、別の障害の起こり方も見えるようになりました。2回目のレビューでは、DB接続プールの競合、Multi-AZ切り替え中の再試行、監査ログ障害、複数タスクのセッション、通知の最終失敗、正式化の再送、JPA例外の発生位置、個人情報の法務確認という8件の重要な課題が見つかりました。

たとえば、監査ログの書き込みに失敗した場合は、重要な業務操作もロールバックする方針を選びました。操作は成功したのに記録がない状態を許さず、`AuditService`の例外を握りつぶしません。

8件を設計文書へ反映したあと、3回目のレビューを行わず実装へ進みました。重大な課題が0件であり、残る問題の一部は実際のコードとテストで具体化できると判断したためです。

実装計画は、Spring Boot基盤とBC-001/002/003、Google Workspace OIDCとBC-005、Next.jsフロントエンド、通知、本番リリース準備の5段階へ分けました。境界コンテキストとリスクの単位で実装し、各段階でテストを通します。
